# Routing evaluation, 2026-10-17

Plan task 14's routing evaluation ran once: every case of the four
`evals/<skill>/routing.yaml` files (81 cases), three repeats, in Claude
Code 2.1.302 and codex-cli 0.162.1, 486 fresh sessions in all, on
subscription logins. Forge was at `8cc2066`. Each case ran through
`live_runs._routing`, which `tools/live_checks.py --case routing` also
uses; a local driver called it in five batches (10, 20, 40, 80 and 93
cases per harness) to measure usage between them. Hashes of the private
evidence, the inputs and the per-batch usage are in
`routing-2026-10-17-index.json`.

## Results

The recorded streams were judged again offline at `97ac5b4`

several files when the skill's `SKILL.md` is the first. That changed
four Codex results from not-run to pass and no Claude Code result.

## What the results show

- **Claude Code misses.** `harness-intake/secret-guard` ("Make sure our
  coding agent can never read the .env files in this repo.") failed in
  two of three repeats: the model chose the bundled `update-config`
  skill, a competing route. `harness-intake/which-mechanism` ("Should
  blocking pushes to main be a hook or something else?") failed twice:
  the model answered without a skill. `build-skill/resolve-conflict` and
  `harness-verify/extensive` failed once each; the second chose
  harness-intake first.
- **Codex harness-research.** In most of its not-run cases the model
  read `harness-intake/SKILL.md` and `harness-research/SKILL.md` with one
  `cat`, intake first. Forge counts the first skill read, as it counts
  Claude's first Skill call, so research is not credited. harness-research
  works from a decision's brief, so reading intake first in a workspace
  without a decision is a defensible order; the case expectations stay
  as written.
- **Explicit invocations.** `/name` in `claude --print` and `$name` in
  `codex exec --json` put the skill into the prompt, and neither stream
  shows an event for it, so these cases report not-run unless the model
  also calls or reads the skill. The generated-skill verification gate,
  which needs a passing explicit case, is a separate check: in the
  earlier vertical and flows runs, 52 of 57 explicit cases passed through
  a Skill call or a read.
- **Codex near misses** stay unobservable: Codex reports no inventory,
  so no run can prove that a skill stayed inactive.

The skill descriptions are unchanged; the misses do not show missing
description wording.

## Corrections during the run

The driver stopped Codex after batch 4 on a false usage-limit match: a
model answer quoted a knowledge-base page that mentions rate limits. The
driver was changed to read only Codex's error events, and the run
resumed at batch 5. No case was lost or run twice.
